# OpenOMF 原版音频剩余适配方案

本文保留历史提案；当前实施状态以文末2026-10-25补充为准。2026-10-24用户允许按需获取和修改SDK源码，并要求把此前修复同步到源码；音频运行时/模拟器/固件扩展尚未实施。此前工具修复已同步到独立SDK源码分支并完成原引擎重建。

## 当前可复现基线

OpenOMF0.2.0已直接运行上游三声道调度器，保留优先级、音高、重复声音处理与音量。APP将原DAT完整采样转成PCM16 WAV，通过四句柄缓存混音。原PSM全曲转换MP3，使用公开get_state在EOF后重播。可在原版单人或锦标赛对战验证。

## 需要公开能力的原因

现有ABI4.1只允许逐音效改变pitch/gain/ramp，缺少播放中的左右增益/声像。当前只能在加载PCM时写入初始声像，原引擎的audio_set_pan不能无中断地更新。

手册确认start_file切换当前背景会话，audio_stop停止全局；未提供独立BGM停止，且音乐切换可能停止音效。原引擎要求音乐切换和EOF循环不干扰正在播放的拳脚、命中和语音。

## 建议实施范围

1. 保持现有4.1结构布局、导入函数、错误码和旧APP行为不变。新增能力以正式版本和能力标记暴露；具体API命名与版本号先对齐SDK设计，不在APP里猜测私有导入。
2. 为每个音效声部增加独立左右增益/声像和采样级渐变，更新参数不重置播放相位。保持四句柄、64KiB和已有优先级由APP控制的限制。
3. 将BGM生命周期与效果声部分离，提供独立背景停止、切换、循环或排队能力；当前效果声部和缓存不受影响。现有全局stop仍维持兼容语义。
4. 固件音频线程推进BGM循环，不能依赖APP的22FPS绘图回调；对MP3解码延时与SD阻塞给出可测量的缓冲/欠载日志，不能直接承诺无缝。
5. 同时更新公开手册、导入白名单和模拟器的对应能力，再在OpenOMF音频适配器接入。保留原audio.c调度器，不改变上游战斗时序。

## 手动验收场景

- 三个原声音同时播放时左右移动机器人，声像变化连续，不能从头重播。
- 对战中切曲或BGM自然EOF，命中声和语音不被截断；菜单返回、暂停恢复不残留声部。
- 反复进入/退出APP后句柄和PCM缓存回到基线。
- 微雪真实SD卡与音乐/三声道复合负载下观察欠载数，模拟器结果不能替代实机结果。

## 与真机内存的关系

目前固定12MiB WASM线性内存，其中8MiB为有界C堆；实际观察C堆峰值约3.74MiB，但未遍历所有机器人/结局。Xtensa AOT整块1,802,820B，尚未证明固件可执行内存可以容纳。进入实机前另需确认可执行代码/数据分段预算和PSRAM余量；不能只按当前堆峰值推断可用。

网络UDP bind/listen、MOD/外部PNG和桌面手柄属于其他尚未完成的能力，不包含在这次音频扩展范围。

## 2026-10-24源码核对补充

独立源码检出在本机aster-sdk/source/aster-sdk，基于最新主分支68d14e2；工具修复位于feature/openomf-audio本地分支，尚未提交或推送。源码重建所得OpenOMF包与安装SDK构建包逐字节一致；旧0.1.1包和原引擎0.2.0包都通过源码校验器。固件与模拟器独立检出在同级source/aster-firmware和source/aster-sim，未修改或烧录。

源码确认固件已经支持AOT的PSRAM执行映射，不能把AOT文件大小直接与内部IRAM比较。目前加载器保留1,802,820B完整AOT镜像，并额外复制1,423,748B TEXT至可执行PSRAM，二者至少3,226,568B；这份重复占用是实机适配应优先解决的问题。加上已观察C堆峰值、其他静态区/栈和Host管理堆，简化下限就约7.97MiB，未计入全部系统开销。具体源码路径与预算见SDK源码docs/openomf-device-notes.md。

## 2026-10-25 实机性能补充（尚未实施的新API）

当前实机基线0.2.11已能在微雪板运行原版自动对战，4MiB线性上限、3MiB APP私有堆；此前12MiB、8MiB私有堆和未刷固件的描述是早期历史基线。已实施的固件改动是AOT输入回收和连续内存布局，音频API扩展仍未实施。SDK/固件源码修改已获用户授权，本文不表示新增API已经可用。

双Nova/ARENA4重负载样本120帧/42055ms，PCM194次、全部缓存未命中，转换及加载13774ms；逻辑23274ms中包含这些同步音效成本，不能全部归因于AI。绘制7917ms、转换3825–4318ms/120帧量级、提交约4.8–5.3秒/120帧。普通ARENA1样本约5.37FPS；复杂场景约2.85FPS，仍不够流畅。

下一步实施优先级：

1. 为SDK正式增加从受限Guest缓冲加载PCM/WAV的公开能力，Host验证完整长度、格式、采样率、64KiB上限和句柄额度，并复制拥有PCM后才返回；保留文件加载兼容行为。固件现入口为systems/zephyr/runtime/aster_native.c:n_audio_effect_load，平台实现platform/esp32s3/audio.c:aster_plat_audio_effect_load。模拟器同步实现与边界语义，手册及校验白名单一起更新，APP不能私自导入未发布符号。
2. 完成本文前述动态声像接口后，按声音ID缓存原速PCM，通过play_ex/set_params应用原版音高、增益和声像，避免把每个频率/声像组合重新生成WAV并写SD再读回。四句柄和64KiB限制先保持；首次声音加载与后续命中分别计时。不能为提高命中率粗化原版音高或删声音。
3. 将原版调色板软件绘制的高频像素循环移到可批量提交的Host原生路径：保留320×200索引、remap/tint/add、透明键、阴影、抖动及原始采样语义。Guest范围检查、乘法溢出、pitch、目标裁剪和临时缓冲预算都必须明确；Host转换后复用现有显示路径，避免再分配整屏副本。公开能力正式版本化并维持旧ABI4.1应用兼容，不能仅在APP加私有导入。
4. 基于现有一次性原版DEMO入口记录同一机器人/竞技场的多段实际帧率、PCM缓存命中/未命中、Guest堆峰值及Host剩余连续块；再观察原版场景切换、暂停/继续、退出回收和三声部并发。结果必须来自实机，不能用申请fps或模拟器fps替代。

APP侧已完成分帧加载、无损稀疏精灵接管、私有空闲链表、32位输出及音效批量SD写入；现阶段不以删除阴影/机关、降低分辨率或改变AI和招式来换取“原版体验”。


## 2026-10-25 实施状态更新

内存WAV加载已实施为本地ABI4.2候选公开接口aster_audio_effect_load_memory(wav, bytes)，能力audio-effects-memory（bit22）。Host验证完整Guest范围、RIFF PCM16、8–48kHz、单/双声道、总WAV最多69632B及PCM最多65536B，复制拥有数据后返回；句柄上限仍为四个。固件、模拟器、SDK契约/头文件/构建能力表/手册同步。不是官方SDK发布。

APP0.2.12起不再把临时音效WAV写SD再读回，仍按需从原SOUNDS.DAT读采样；保留原调度与精确初始音高/声像。动态声像和独立BGM切换/停止尚未实施，本文对应提案仍待完成。当前0.2.14真实设备4MiB线性/3MiB C池，已跨原版DEMO场景运行；12MiB及未部署描述仅为历史。

0.2.14实机120帧样本约4.0–6.3FPS，C池观察峰值2799760B，仍需继续优化原生像素处理和显示提交。完整结果见README最新章节；不能把内存API完成当作全音频或全流程验收。
