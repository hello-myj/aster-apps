# Aster 固件连续音效实施方案（供固件侧直接执行）

日期：2026-10-21  
状态：实施规格；下述新增接口尚未存在，不得当作当前 SDK 已提供的 API。  
目标设备：ESP32-S3 微雪 waveshare35b；当前公开 ABI 4.0.0，8 MiB PSRAM。  
范围：连续引擎声、实时变调/音量、音乐与音效稳定混音、故障统计，以及对应 SDK/模拟器适配。APP 绘图优化另行进行。

## 0. 可直接交给固件执行方的任务

请在固件仓库中定位音频服务、I²S 输出、MP3 解码、WASM/AOT native 导入绑定、APP 生命周期资源回收、板级功放配置，以及 SDK 与模拟器音频适配代码，按本文实施。本文没有检查固件源码，具体模块路径和内部函数由执行方核实，不要凭名称新建一套重复的音频服务。

先复现并记录现有行为，再按最小增量扩展现有四个音效槽。保留旧 API 的行为和旧 APP 兼容性；新增循环、变调、淡入淡出、逐音效停止及诊断接口。完成固件、SDK 头文件/native 绑定、模拟器、开发手册及真机验收后交付。不要只修改 APP 定时重复播放，也不要只新增头文件而遗漏固件导入绑定。

先提交接口与当前内部实现的映射、预计额外 RAM、采样率策略及任何必要的契约调整；接口细节可按项目规范调整，但必须同步文档、绑定、模拟器与示例，避免两侧使用不同协议。

## 1. 已核实的现状与复现入口

游戏工程：E:\个人项目资料\aster\APPS\OutRun  
当前 SDK：E:\个人项目资料\aster\aster-sdk-4.0.0-windows-x64-2c9f7b5af80a\aster-sdk  
当前源码：src/port/game.c 的 audio_prepare、audio_begin、audio_tick、audio_end。  
实机日志：artifacts/device/effects-verification.log、runtime-verification.log、final-memory.log。

当前公开接口只有 effect_load(path,len)、effect_play(handle)、effect_unload(handle)；effect_play 同句柄重播会从头开始。四个音效槽，每个最多 64 KiB 的原生格式立体声 PCM WAV。背景音乐 start_file 是独立的后台播放会话。

引擎/刹车片段约 0.315 秒，APP 每 19 个 60 Hz 逻辑步重新触发。名义间隔约 0.3167 秒，本身不是无缝循环；真实 APP 仅约 4–5.4 FPS，回调抖动和每帧最多补 150 ms 的逻辑策略进一步拉长间隔。这是引擎断续的已确认 APP 层原因。即使显示停在上一帧，固件也必须能独立连续播放已经启动的循环音效。

实机音效加载已成功：rate=16000，crash=1、engine=2、beep=3；用户确认背景音乐和倒计时可听。短音效已改成标准 fmt/data PCM WAV 头，不含 LIST 元数据。

实机还有以下需要独立定位的警告：

- audio_get_info 的原生格式为 16000 Hz、双声道；MP3 日志显示 native output 22050 Hz、双声道、I2S block=1024。格式切换是否正确，必须检查实现；不能只凭日志断言已经有采样率错误。
- player feed -EIO, prepare I2S；必须记录出错阶段、队列水位、解码/混音/输出耗时，确定是否欠载、状态机或驱动问题。
- pa gpio not ready；用户仍能听到声音，应核实此板功放是否有可控 GPIO，不能直接认定功放坏或盲目改引脚。
- invalid AXS15231B touch frames 在游戏前已存在，属于另一个驱动问题；本任务不以屏蔽触摸日志代替修复音频。

内存基线：游戏 Guest peak=2703360 B（2.58 MiB）；运行时仍有至少 2 MiB 连续空闲 PSRAM 块。该数不是全系统音频可用预算；sys mem 中 PSRAM 97% 是预留池总额，不是实际只剩 3%。新增分配前必须记录真实堆分配情况与峰值。

## 2. 完成后的行为

1. APP 调用一次循环播放后，音效持续到显式停止/卸载/APP 退出，无需每帧续播。
2. 调整 pitch/gain 不重置播放位置，不重新读 SD、不重新分配音效缓存。
3. 最多四个已加载音效可同时活动，与一条背景音乐混音。复用现有上限，本次不要求无限声部或多实例音效。
4. 每个 effect handle 对应一个活动播放实例；同句柄 play/play_ex 重触发的行为明确，不偷偷额外占槽。
5. 引擎、刹车支持循环；起跑和碰撞支持一次性播放；任何一项可独立停止，不能通过停止背景音乐来停止引擎。
6. APP 低帧率、短时绘图/SD 高负载时，音效不依赖 FRAME 回调推进。APP 真正暂停时冻结其音效相位，恢复后继续；退出/崩溃/卸载后可靠释放。

## 3. 建议的公开接口契约

以下为建议的新增 ABI。类型全部固定宽度，不含跨 ABI 指针、bool 或编译器枚举；size/version 采用现有项目规范。实现方最终确认接口后再分配 feature bit、导入项和 ABI 版本，本文不预占编号。

```c
#define ASTER_AUDIO_EFFECT_F_LOOP 1u

typedef struct {
    uint32_t size;
    uint32_t version;          /* 1 */
    uint32_t flags;            /* 首版仅支持 LOOP；未知位拒绝 */
    uint32_t loop_start_frame;
    uint32_t loop_end_frame;   /* 排他端；0 表示源样本总帧数 */
    uint32_t crossfade_frames; /* 源采样帧；0 表示不用接缝交叉淡化 */
    uint32_t pitch_q16;        /* 65536=原速，建议首版 32768..131072 */
    uint32_t gain_q16;         /* 0..65536 */
    uint32_t fade_in_ms;       /* 建议允许 0..1000 */
} aster_audio_effect_play_desc_t;

typedef struct {
    uint32_t size;
    uint32_t version;          /* 1 */
    uint32_t pitch_q16;
    uint32_t gain_q16;
    uint32_t ramp_ms;          /* 两个参数平滑到目标；0=立即 */
} aster_audio_effect_params_t;

int32_t aster_audio_effect_play_ex(uint32_t handle,
    const aster_audio_effect_play_desc_t *desc, uint32_t size);
int32_t aster_audio_effect_set_params(uint32_t handle,
    const aster_audio_effect_params_t *params, uint32_t size);
int32_t aster_audio_effect_stop(uint32_t handle, uint32_t fade_out_ms);
```

约束：

- 成功返回 0；失败使用 SDK 现有负错误常量。无效句柄、错误 size/version、越界循环点、溢出尺寸、未知 flags/不支持能力均给出明确错误，不静默截断坏参数。
- frame 指一个采样时刻的完整声道组，立体声 frame 是 L/R 一对，不是单个 int16 样本或字节。
- LOOP 时必须满足 0 <= start < end <= 总帧数。crossfade_frames <= 循环长度的一半；过短、过大的范围拒绝，不能读越界。非 LOOP 的循环/交叉淡化字段应为 0，否则拒绝。
- play_ex 从样本起点开始，可先播放 loop_start 前的引入段；到 loop_end 后按循环区间继续。若选择其他行为，必须在最终契约明确并同步模拟器。
- play_ex 与旧 play 均可重触发同句柄；set_params 永不重置相位。gain=0 只静音，循环仍推进；stop 才结束实例。
- stop 仅作用于对应句柄；对已停止但仍有效的句柄幂等成功。fade_out_ms=0 可立即停止，正常游戏使用约 10–30 ms 淡出。
- 卸载正在播放的音效时必须安全摘除并释放，不能留下音频线程悬空指针。
- 旧 effect_play 保持一次性从头重播及既有默认音量语义，不能升级后默认变循环。

诊断能力另增加一个带 size/version 的状态查询（名称按项目风格，例如 audio_get_diagnostics），至少返回：实际 output_rate/channels/bits、active_effects、BGM 状态、输出队列当前/最小水位、underruns、I2S 恢复次数、命令丢弃数，以及各类内存当前值/峰值。累计播放帧数用显式 uint64 或 lo/hi 字段，布局与对齐在 Guest/Host/模拟器一致。计数口径、复位时机、是否包含启动预缓冲必须写清楚。

## 4. 音频线程与混音实现

### 4.1 独立推进与所有权

- 扩展现有后台音频 worker；无需新造一个由 APP FRAME 驱动的混音循环。
- 即使没有背景音乐、只有一个循环音效，也必须维持 I²S 输出。BGM EOF/stop/seek/换曲不能误清空循环音效状态。
- 每块输出按采样帧推进每个 voice 的 source phase；时间基准是音频输出时钟。
- APP 命令通过有界队列/参数快照送入 worker，短锁保护状态；音频热路径不做 SD 访问、动态分配、长锁或高频日志。
- 连续参数更新允许按句柄合并，只保留最新值；play/stop/unload 的顺序不能丢失。队列满时明确返回忙或执行已约定的合并策略。
- stop/unload/APP destroy 与正在混音的 voice 通过确认机制、引用计数或短临界区安全交接。命令对象不能持有回调结束后失效的 Guest 指针。

### 4.2 重采样与平滑

- 使用足够宽的定点相位累加器，防止长时间循环溢出；步长为 source_rate/output_rate × pitch_q16，乘除采用防溢出的中间类型。
- 双声道采用同一个相位，以线性插值作为首版质量基线；循环边界的插值邻点也必须正确回绕。
- pitch、gain 在 ramp_ms 内按输出采样时钟平滑到目标，默认游戏建议 10–30 ms；不能只在下一次 FRAME 修改一次音频相位。
- 循环接缝支持交叉淡化，并明确交叉区的回绕/相位策略。若重叠导致实际循环周期缩短，要在文档记录；不要重复播放交叉区而产生节奏跳变。
- 所有声部累加使用足够宽的中间值，最终饱和到 int16；绝不允许整数回绕。BGM/effect 各自有增益，最终再应用系统音量。
- 变速播放允许音高与速度一起变化；首版不要求昂贵的保时变调算法。

### 4.3 I²S 输出与采样率

先检查当前源格式和输出格式切换实现，再选择统一策略：

推荐在同一个活跃混音会话内保持稳定输出采样率（例如设备适合的 22050 或 44100 Hz，由固件侧验证决定），将 BGM 和 effects 都转换到该输出格式。若继续允许 MP3 原生采样率切换，则切换必须走完整、同步且可观察的状态机，不能让仍在运行的 effects 继续使用旧步长或旧 DMA 配置。

保留 audio_get_info 对旧 APP 的原生 PCM 输入契约，不要静默改成“任意当前 MP3 采样率”。实际输出格式由新增诊断字段报告。新 effect API 使用加载时明确记录的源采样率，不猜测。

- 以约 10–20 ms 输出块作为起点，根据实测调节 DMA/队列；在可抢占调度下音频 worker 优先级应能及时供给 DMA，不能被 APP 像素绘制长时间饿死。
- 区分 MP3 读取/解码 FIFO、混音缓冲、I²S DMA 队列。一个 FIFO 的容量不代表另一个队列有足够数据。
- 输出缓冲目标约 40–80 ms，兼顾变调响应；容量可以更大，但不要长期灌满成数百毫秒控制延迟。
- 初始预缓冲后再启动；欠载时计数，短暂补静音并受控恢复。调查每次 -EIO 根因，禁止用无限 prepare/restart 循环或关闭日志掩盖。
- MP3 解码失败、EOF、SD 短暂阻塞和 I²S 失败应分别记录，不合并成一个含糊 -EIO。

## 5. WAV、内存和板级要求

### 5.1 WAV 兼容

支持 RIFF/WAVE PCM16，按 chunk 解析 fmt/data，正确跳过 LIST/JUNK 等未知块及奇数字节 padding；检查 chunk 长度、文件边界、blockAlign、声道、采样率和整数溢出。至少保留现有标准 44 字节 PCM WAV 支持。先验证再发布句柄，失败不得泄漏槽位或缓冲。

现有四槽、每个 64 KiB 上限继续保留，循环不是把片段重复复制成几分钟长文件。当前 16 kHz、双声道、16 bit 的 0.315 秒片段约 20 KiB；四个约 80 KiB 采样数据，通常已包含在旧功能预算中。新增部分应主要是相位/参数和小块混音缓冲。

### 5.2 内存预算与调度

- PCM 缓存、解码 FIFO 等可放 PSRAM；DMA 使用满足 ESP-IDF/Zephyr 当前驱动要求的内存，不凭猜测把 DMA 直接移到 PSRAM。
- 示例：16 kHz 双声道 PCM16，40–80 ms 输出数据为 2560–5120 B；22050 Hz 时约 3528–7056 B。还要另计 DMA、解码器、任务栈及控制结构。
- 不要给每个 voice 分配一个大输出环；四个 voice 混到共享输出块。首轮以额外 PSRAM <=64 KiB、额外内部 RAM <=16 KiB 为设计目标，最终以实现的分项实测为准；超预算时说明原因。
- 首轮使用现有工作线程或记录新增线程栈预算。未证实前不要固定绑核；先检查显示、Wi-Fi、SD 和音频现有优先级与锁关系。
- 新增诊断不得在每个采样点读取高开销系统时钟；按块统计，低频输出汇总。

### 5.3 功放

检查 waveshare35b 的设备树/板级配置和真实连线。有 PA 控制脚则正确配置使能/静音时序；没有可控 PA GPIO 则作为合法配置处理。不要使用未经板级资料核实的 GPIO，也不要把“GPIO 可选不存在”打印为每次播放都发生的硬件故障。

## 6. SDK、ABI 和模拟器同步

- 现有 ABI 4.0 APP 必须继续加载运行；旧 effect_play 行为和现有结构布局保持不变。新增独立结构，不直接扩展旧 audio_info 的布局语义。
- 固件实现 native 导入、Guest 参数/越界/权限验证，支持解释执行及 Xtensa AOT 同一路径。数据必须复制到 Host 自有状态后异步使用。
- SDK 补齐头文件、工具导入校验白名单、feature/版本说明、API 文档和最小示例；若有自动生成流程，更新源定义而不只修改生成文件。
- 由维护者按项目发布规则分配 ABI 小版本和 feature bit。新 APP 声明实际需要的最低版本，或提供独立旧版构建。
- 注意：如果 WAMR 在加载阶段拒绝缺失的 native import，APP 内先 has_feature 再调用新函数不能解决兼容加载。必须使用真实可行的导入兼容方案或明确最低固件版本，不得只加 if 判断就宣称旧固件兼容。
- 模拟器增加等价的 loop、pitch、gain、ramp、stop、pause/resume、cleanup 行为；无声/离线模式也推进可查询状态。模拟器通过不能替代 I²S 真机验证。

## 7. OutRun 后续接入约定（由 APP 侧实施）

1. 仍只加载 crash、engine、start、brake 四个 effect。
2. 进入行驶状态只调用一次 engine play_ex(LOOP)，删除 steps%19 的重播逻辑。
3. 根据速度、档位、油门更新 engine pitch/gain，使用 ramp。具体转速映射由 APP 对照原版调校；固件不要硬编码 OutRun 车速公式。
4. brake 独立 loop 或短音效，按开始/结束制动切换；引擎降音量而不是每帧停止再从头启动。碰撞 one-shot 与两者混音。
5. 起跑 one-shot 不循环；停止、暂停、超时、重试及退出正确清理所有 voice，背景音乐单独管理。
6. 音频状态更新可随 APP 最新状态发送，但音频持续播放不依赖更新频率。5 FPS 时参数变化会更粗，不能由固件凭空补出未收到的驾驶操作。

## 8. 实施顺序与可回退交付

第一步：基线诊断。记录现有优先级、内存、输出格式状态机和欠载；复现 BGM + effects 下的 -EIO。明确保留的旧接口行为。

第二步：固件循环与停止。复用四槽，实现 source phase、loop、生命周期回收；即使 BGM 未启动也能输出。

第三步：pitch/gain、插值、ramp 和循环接缝；处理不同源采样率、BGM 启停、换曲、EOF 与输出格式状态。

第四步：修正 I²S/FIFO/调度问题及可选功放配置；保持正常场景不出现欠载和反复恢复。

第五步：同步 SDK/模拟器/手册/示例，构建发布包；交付版本对应关系和导入兼容说明，再给 APP 侧接入。

旧固件和现有 .ast 保留可回退备份。实机刷写前提供准确板型、镜像路径、配置、分区变化说明、恢复方法，并遵循用户的烧录授权；本方案本身不授权擦除 SD 或无关 Flash 分区。

## 9. 验收（本任务明确要求执行并保存结果）

### 基础与边界

- 合成 PCM 夹具验证循环边界、立体声帧、线性插值、Q16 pitch=0.5/1/2、音量 0/1、ramp、淡出和饱和，包含极短循环、非零 loop_start 和交叉淡化。
- 非法句柄、坏 size/version、坏 Guest 指针、溢出长度、越界循环点、未知 flags、坏 WAV chunk 明确失败，无越界/崩溃/泄漏。
- 更新 pitch/gain 不重触发；gain=0 后再恢复可继续同一实例；stop/unload 可安全并发。

### 实机连续性

- 无 BGM 时单独连续引擎循环至少 10 分钟；只调用一次 play_ex，期间 APP 不续播。
- MP3 BGM + engine loop + brake loop + crash one-shot 同时工作，持续至少 10 分钟；起跑测试另起一次，不要求超出四槽上限。
- 把 APP FRAME 限到 5 FPS，并加入符合现有回调期限的显示/SD 压力，至少 2 分钟。循环仍连续，日志给出欠载、I²S 恢复、队列最低水位和命令延迟。
- 预热后正常场景以新增 underruns=0、无持续 -EIO 恢复为通过目标。故意制造欠载的故障注入用例另外记录，不能和正常用例混淆。
- 起跑、油门、换档、松油、刹车、碰撞、BGM EOF/stop/换曲、APP pause/resume/retry/stop 均验证；暂停后无残留声音，恢复相位策略符合契约。
