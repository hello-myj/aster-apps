# 应用商城与资源分发

第一版包含本地 Python HTTP 服务、设备商城 APP、设备能力查询和受权限控制的延迟安装。
服务器运行在 Windows、Linux、macOS 的 Python 3.11+，在 APPS 根目录启动。
本地使用 HTTP；公网阶段使用 HTTPS 域名与反向代理，不把开发服务器直接当作公网生产服务。

应用源工程继续按现有方式放在仓库根目录，每个工程自行拥有源码、原始素材、转换工具。
`build/`、`dist/`、运行时数据和资源转换产物不提交。`StoreServer/` 保存服务端代码；
`AppStore/` 保存设备端商城；`StoreServer/data/releases/<摘要>/` 保存不可变发布快照。
不移动现有工程，不把某个游戏的资源原件放进别的游戏工程。

发布单元是“APP ID + 版本 + AOT 目标 + 明确支持的开发板”，包含程序 AST 和独立资源树。
AST 内资源继续由原安装器处理；大资源通过独立文件下载，避免打成一个巨型 AST 并一次加载到 PSRAM。
每个文件记录相对路径、字节数、SHA-256。发布目录不可变，下载由摘要定位，支持 Range。
资源进入应用当前代码版本的 `/assets`，用户存档仍在 `/data`，更新不覆盖存档。
资源使用版本目录，与代码一起切换；未下载完或校验失败时不安装，不让新代码引用半套资源。

已有游戏中直接访问 SD 固定目录的资源需要逐项迁移到 `/assets`；没有完成迁移和目标板测试的
构建不能宣称已适配。商城不会仅因为存在一个同架构 AST 就自动上架到所有同架构开发板。

兼容检查使用真实设备的开发板 ID、AOT 目标、ABI、屏幕尺寸、能力位。
服务端在列表和下载入口都检查；商城复核元数据；固件安装器再次验证 ABI/AOT/签名。
发布必须显式提供开发板白名单，未知硬件默认不提供下载。
不同 AOT 后端各自发布，资源相同也不混用二进制。

商城具备列表、应用详情、权限/下载体积提示、下载进度、取消、失败重试、服务地址设置。
下载分块写入商城自己的暂存目录并逐文件计算摘要，不把应用包或资源整体留在 WASM 内存。
安装申请使用 `appmgr` 权限，只接受调用者沙箱内的文件；商城退出、VM 释放后再安装，完成后返回商城。
安装结果持久化，重启后可以显示；安装失败保留现有应用的活动版本。

当前范围是可信局域网验证。SHA-256 检查传输完整性，不冒充来源认证；公网发布还需要
可信 HTTPS、签名/信任策略、下载限流、发布权限和资源许可证审核。HTTP 服务不开放上传和远程发布接口。

## 当前验证范围

服务端在 Windows 上运行，Windows 和 WSL/Linux 均通过启动 HTTP 服务的接口测试；macOS 实际运行仍待验证。商城已编译 RISC-V 和 Xtensa AOT，P4 上已启动商城并通过 Wi-Fi 获取局域网服务器目录；S3 实机尚未验证。

模拟器已使用真实商城 WASM 完成 HTTP 下载、退出商城后安装、重新进入商城、打开演示应用的完整流程；验证独立文字资源和 1 MiB 图案资源。模拟器安装目录目前仅在当前会话保留。固件测试验证流式资源复制、失败回滚、禁止自更新及安装队列权限/结果处理。P4 实机已通过商城下载和安装 StoreDemo 1.0.1，并以 RISC-V AOT 启动，日志确认 `STOREDEMO PASS external message and 1048576-byte resource`。

SDK 单元测试 108 项通过，固件 140 项通过、3 项跳过；模拟器 93 项通过、25 项因缺少集成样例跳过。构建与测试不能代替未完成的板级实机验证。
